# FarField 系统可行性审查与模块评测方案

日期：2026-10-09。审查对象为 `FEEDBACK_COMPLETION_EVAL_VALIDITY.zh-CN.md`、当前生产入口、调用适配器、原生评价与已有外部任务接入。

原方案方向正确，但只能作为诊断报告和改进提纲，还不是可直接执行的完整生产优化方案。需要补上请求生命周期、修复路径、评价器语义、最终交付选择和各模块的独立验收。原报告的测试通过数与四个开发 claim，均不足以排除这些缺口。本轮没有修改生产实现或重新付费调用模型；新增了可重复的离线故障审计，结果不是科学能力分数。

任何开放科研系统都无法承诺以后没有错误或第三方超时。可实现的目标是：故障可观测、预算有边界、状态不损坏、可恢复故障能够恢复，未解决问题不会被表述为科研成功。可靠性需要用故障覆盖、恢复率、失败后损失和质量—成本曲线验收，而非用单次无报错代替。

## 原报告需要修正的判断

| 项目 | 审查结论 | 必要修正 |
|---|---|---|
| 分项指标定位错误 | 可行，但仍是阶段诊断 | F1 不能定位到具体 claim、文档、句索引，也不能自动定位代码根因；区分输入校验错误、测量错误、评分失败 |
| 干预按声明发生 | 当前实现不足 | 只比较 JSON 是否变化，没有检查预测方向、幅度、单位或容差；应将变化检测与预测检验分开 |

| 最后失败就交付失败 | 仅适用于明确的最后提交协议 | 开放优化应允许保留仍有效的已验收候选；新尝试失败不能自动抹掉旧交付，但最终选择必须显式记录，不能事后挑隐藏测试最高分 |

## 代码与故障注入发现

运行：

```bash
PYTHONPATH=src /tmp/farfield-science-venv/bin/python \
  scripts/eval/audit_runtime_reliability.py \
  --out /tmp/farfield-runtime-audit-new.json
```

输出路径必须尚不存在。退出码 2 表示发现需要审查的差异，不是脚本运行失败。脚本使用本地注入的传输结果，不访问 API，不生成科学题，也不使用 LLM 评分。

### 调用账本没有覆盖完整请求生命周期

生产路径 `extras/openworld/runtime.py` 使用 `extras/llm.py`，主要适配器测试 `tests/test_llm.py` 引用 `services/llm.py`。两份实现目前传输逻辑基本重复，只在基础依赖等处不同；不是已经证明行为分叉，但具有维护分叉风险，异常类也不是同一类型。

两份适配器均复现：

| 故障注入 | 实际行为 | 风险 |
|---|---|---|
| 额度为一次，连续发起两次逻辑调用，每次都超时 | 共发生 6 次传输，账本仍记录 0 次消耗，剩余 1 次 | 成功返回账本不等于 HTTP 尝试预算，恢复后可能继续消费，超时账单未知 |
| 供应商响应体不是合法 JSON | 保留 1 次预留、0 次消耗，未保存响应文件 | 槽位泄漏、故障证据丢失，后续调用可能误报预算耗尽 |
| 两个线程请求相同内容 | 发送 2 次，账本只记 1 次和 10 token | 缓存去重发生在发送以后，掩盖实际开销 |

评测中的 `CampaignClient` 另有独立尝试上限，限制了此前小实验的请求数量；上述发现不能据此改写旧实验为“无限消费”。它也通过修改模块全局变量关闭重试，且在传输层追加 `max_tokens`，这些政策没有统一进入生产客户端与缓存请求身份。

评测传输为 75 秒且无重试；生产默认每次传输 300 秒、最多三次尝试。`urlopen` 的 timeout 不能当作整个研究任务的绝对截止时间。此前仅两次超时，无首字节／完整响应等分段遥测，无法断定是上下文、推理量、代理排队还是网络导致。直接延长 timeout 或添加重试没有解决这个识别问题。

### 操纵检查没有验证预测

`services/native_evaluation.py::check_intervention` 对 baseline=10、candidate=5、预测“增加到 10 以上”、控制值不变，仍返回 `observed_as_registered`。它确实正确识别数值发生变化，并保留 `mechanism_support=not_assessed`；问题是状态名称可能被解释成预测已实现。

应分别表示：

- 指定实现是否启用、指定变量是否改变；
- 改变是否满足独立定义的方向、量纲、幅度与容差；
- 控制条件是否满足、实验是否有区分能力；
- 结果是否支持具体机制，竞争解释是否仍成立。

前两项不能靠解析模型自由文本做可信判断。宿主按领域定义可计算谓词，模型可以提议，定义和适用范围必须在确认实验前冻结。改变可观测量但预测失败并不矛盾，更不自动推翻机制。

### 其余影响整体能力的限制

- `paired_native.py` 只开放 IDEATE、EXPLORE、CRITIQUE；远跳检索被设为 `offline_corpus_only`。允许一个动作不等于它在轨迹中实际执行。旧结果不能衡量完整技术脉络检索和远跳落点研究，也不能证明经过校准的 OpenWorld 发挥作用。
- 结果回应在执行新程序前检查，缺一项测量声明就拒绝整个候选。应允许已定位的实现修复走较短路径，但仍必须回应相关新结果，不能代填科学判断或绕过撤回。
- 当前重跑要求输出字节完全一致，适合限定的确定性文件任务。随机训练、无关文件顺序、浮点差异需要分别制定复现规则；不能为了扩大覆盖而取消原始产物追踪。
- 依赖图主要覆盖 idea、开放执行、原生评价和比较，并未统一全部论文结论、WORLD 证据和学习技能。回应过某结果与科学上依赖该结果应区分；否则撤回既可能遗漏，也可能过度传播。
- 原生得分、代码哈希和协议字段完整，不等于科学操作正确。正确的验收还需要任务特定的单位、样本、控制、实现和语义校验。

原始记录：[runtime-probes.json](../docs/audits/2026-10-09-system-feasibility/runtime-probes.json)。共 7 条差异，是三类适配器问题各在两份实现中复现，加一项干预语义边界；不是七个独立科学失败。

本轮在真实 namespace 可用环境重新运行 `test_llm`、`test_result_response`、`test_native_feedback`、`test_native_evaluation_loop`，55 项全部通过，无跳过。通过的既有契约与新故障探针同时成立，说明测试覆盖不足；不能用通过数否定已复现问题。本轮没有改动生产逻辑，因此未重复整套主测试或进行新的付费模型评测。新审计脚本通过编译，仓库差异检查通过。[验证记录](../docs/audits/2026-10-09-system-feasibility/verification.json)

## 系统优化应采用的统一结构

保留一个生产控制器，逐步收敛重复实现。每次动作围绕以下持久状态流转：

`准备 → 预留预算 → 记录开始 → 实际执行 → 保存原始产物 → 核验 → 回应 → 继续或恢复`

请求、执行、观测、评价、科学主张和最终提交分别有身份。超时是执行状态，不是科学结论。摘要是事件日志的视图，不是新的事实来源。

| 层 | 需要的改动 | 完成条件 |
|---|---|---|
| 模型与传输 | 收敛为一个客户端，旧路径先做兼容导出；实例化重试政策；记录每次物理请求、未知账单与解析失败；并发同请求在发送前合并或完整记账 | 限流、超时、损坏响应、并发、重启均无槽位泄漏和漏计；缓存身份包含有效生成参数与版本 |
| 恢复与调度 | 区分传输重试、结构修复、实现修复、实验重设计；总体 deadline 与有限重试共同约束；读取 Retry-After，使用有界退避 | 恢复不重复执行已完成外部动作；永久错误不盲重试；预算耗尽保留可用交付及未决状态 |
| 开放执行 | 对接隔离项目目录、原生工具和容器生命周期；保留 CPU/GPU、输入与产物身份；按任务支持检查点 | 在完整外部任务上从原始输入到原生评价跑通；不能只用简化 Python 脚本替代 |
| 测量 | 错误含阶段、产物、行／字段、实际值、允许范围；分离输入有效性、程序执行、科学有效性和评分 | 正确及等价正确实现通过，关键单位／样本／控制错误被识别，基础设施失败不变成科学零分 |
| 结果使用 | 根据当前未回应的结果生成最小回应要求；确定性身份由宿主绑定，科学解释由模型作出 | 遗漏字段能局部修复；新结果影响或有理由不影响下一步；无依据结论不因格式齐全而放行 |
| 完成与撤回 | 显式区分候选、已验收 incumbent、最终提交、科学主张；撤回沿类型化支持关系传播 | 新分支失败不抹掉独立有效交付；选中依据失效则更新完成状态；保留所有失败记录 |
| 知识与远跳 | 未知量驱动检索；技术草图核查；来源机制到目标结构到开放实现；补查落点相近工作与失败路线 | 评价能追踪候选为何被选择、实现是否忠于机制、后续跳跃是否使用真实反馈 |
| OpenWorld | 独立保存环境能力与模型预测；问题拆解可修订；先建设测量再积累可比较预测 | 既测预测覆盖与误差，也测实际信息收益和最终表现；错误区间不直接反驳机制 |
| 上下文与学习 | 当前决策依赖、未回应结果、反例、撤回为工作集；原始事件可按需取回；技能先在任务内验证 | 压缩后关键事实提取与实际决策不退化；任务间无未经审查的错误经验传播 |
| 预算 | 计入知识模型、搜索、执行、重跑、评价和恢复；为交付保留依据成本估计的余量 | 多预算点的质量与完成率可复现；不会前期耗尽后无力验证；不假装已有校准 VOI |

重试只适用于暂时性服务故障，并计入双方相同的总预算。连接超时、响应中断与调用已经完成但确认丢失具有不同语义。外部副作用动作必须核查已有回执或使用服务支持的幂等机制，不能笼统重发。服务长期不可用时应有界停止并可恢复，这仍是失败记录，不能承诺最终一定成功。

## 用外部 benchmark 定向测试各模块

这里的模块测试只替换被测环节，其他输入采用冻结的真实材料或轨迹。模块通过以后，还须放回同一个完整运行时验证。模块分数不加总为通用科研能力分数。

| 模块 | 任务来源与具体测试 | 主要指标与对照 | 边界与接入状态 |
|---|---|---|---|
| 检索与证据定位 | SciFact 原生标签；AgentIdeaBench 原生 SEARCH/FETCH，保留时间截止 | 证据召回、支持关系、引用准确性、搜索成本；Static／Active／Replay | 已有 SciFact 开发适配；AIB 目前仅入口烟测，不是完整官方协议 |
| 技术脉络 | AIB 主题下的真实论文、引文及负面结果，逐条核验模型草图 | 技术变化事实准确性、未证实因果叙事比例、遗漏路线 | AIB 本身不提供技术演化因果真值；这部分需独立领域审查，不能自造唯一正确发展史 |
| 问题形成 | 借 CompMat-Bench 的指导强度×工作流长度设计，同一目标与验收 | 不给方法提示后的交付变化、假设修订是否有观测依据 | 代码数据尚待发布；可借设计，但自建输入变体须单列，不能称官方分数 |
| 原生执行 | Terminal-Bench-Science 固定版；PaperBenchX 的 CPU 原生任务 | 产物验收、工具故障、有效执行成本、恢复成功率 | 本机 Docker 可用，当前科学虚拟环境无 Harbor；FarField 原生项目适配尚缺 |
| 测量语义 | PaperBenchX 原生数值检查／rubric、SciFact 可定位校验 | 原生数值项、实现符合性；正例、等价正确例、关键错误对照 | PaperBenchX 部分评分包含模型审核；确定性和模型分数必须分开，解释需抽样盲审 |
| OpenWorld 预测 | 可实际改变结果的原生任务；在执行前绑定变量、单位、输入条件和预测 | 覆盖率、误差／适当评分规则、有效实验产出、成本 | 合并不同物理量的误差没有意义；仅在定义可比较的类别内评估 |
| OpenWorld 结果使用 | 将同一外部任务真实观测交给不同控制器；另外自由探索 | 错误归因、重复无效实验、下一步可执行性和后续独立结果 | 同观测对照测使用，自由探索测获取，两者分别报告 |
| 远跳生成 | AgentIdeaBench 真实主题与时间截止，局部／普通跨域／机制引导 | 核查可行性与已有工作；官方 critic 仅作辅助 | 文献阴性检索不是新颖性证明；专家不知道候选来自哪一臂 |
| 远跳实现 | 在允许方法改变的外部目标上，把候选实际实现并做机制消融 | 全部候选中验证有效比例、成本、无效干预率；独立终测 | 严格复现任务不能任意更换方法；拓展成创新任务必须另立协议，不能借官方分数 |
| 依赖与撤回 | Mr.LHDR 隐藏依赖思路＋真实科研执行轨迹上的失效事件 | 无效依据继续使用、遗漏撤回、误伤独立结果 | Mr.LHDR 的 DACS 测已陈述结论，不证明真实执行因果链；其 LLM judge 不作唯一裁判 |
| 上下文与预算 | 对相同外部轨迹使用完整历史／依赖工作集／简单截断；多预算点 | 关键反例保留、实际决策与质量、token、延迟、恢复费用 | OSWorld-Science 仅借配置消融方法；没有 GUI 工具时不声称接入其完整榜单 |
| 系统可靠性 | 从实际故障类别出发，对生产入口注入 timeout、429、断连、损坏 JSON、重启 | 物理请求计数、重复副作用、状态完整性、恢复率 | 工程故障测试不承担科学能力结论；不需要付费模型裁判 |

### 原报告未充分估计的接入成本

PaperBenchX 公开的是 12 个任务，81 个受限任务不在公开仓库。01–03 需要商业软件环境；04–08、10、11 有 CPU 构建路线，但原生任务和验证可能需要数小时；09、12 另有 GPU 条件。公开包不提供参考 solution，所以不能照搬 Terminal-Bench-Science 的 oracle 校验。PaperBenchX 的模型审核也不能因部署在独立进程就升级为独立科学真值。[任务资源](https://github.com/UniPat-AI/PaperBenchX/blob/main/docs/tasks.md)

AgentIdeaBench 公开数据去除了部分摘要、原始检索文本等内容，需要按官方方式重新取得材料。Replay 控制必须共享实际获取的同一份材料快照，不能两臂分别重新搜索后称资料相同。[数据卡](https://github.com/HKUST-KnowComp/AgentIdeaBench/blob/main/DATA_CARD.md)

Terminal-Bench-Science 官方建议在实际环境运行 oracle 五次确认任务稳定。应先固定发布版和任务范围，再运行参考解；环境不能运行的项目按事前资源规则标记。不得看到 FarField 解不出以后把任务排除。[运行说明](https://github.com/harbor-framework/terminal-bench-science)

## 分阶段推进与验收

1. **先修可靠性底座。** 收敛调用器，完善物理请求账本、持久状态、故障分类和局部修复。用上述故障审计及真实旧轨迹核验；账本一致、预留可结算、重启不重复执行是进入付费比较的门槛。网络短测只测延迟和服务稳定性，不混入科研分数。
2. **打通一个完整原生任务。** 接入原生项目执行和隐藏评价；先验收环境与评价器，再以同模型、同工具跑自由 agent 与 FarField。该任务仅作开发，不能循环修改直到赢再当正式结果。
3. **扩展模块诊断。** 从外部任务按领域与资源事前抽取开发集，先测最可计算的执行、测量、证据使用；知识脉络和机制解释保留独立审核。不同时对所有模块、预算和模型做巨大笛卡尔积。
4. **完整系统消融。** 在模块已可达的任务上运行 OpenWorld 开／关×远跳开／关四种配置，加自由 agent。关闭模块只移除其策略，不剥夺基本工具或错误反馈；记录实际激活率。共享观测实验另列。
5. **锁定未参与开发的正式任务。** 任务数依据开发集方差、最小有意义收益和可用资源确定；按原研究聚类。至少报告最终交付率、全体任务口径、条件质量、错误类型、独立有效实验成本和成本—质量曲线。未交付不是测得零，但需要进入失败分母；也可预先定义交付效用为零，并与原生科学分数区分。

原报告的“6–12 题、每题三次”只适合作为候选开发规模。对于数小时原生任务，应先测 oracle 或合法参考流程的实际耗时，再决定可负担样本数。不能声称这个规模已足以证明统计显著提升，也不能把三次重复当三项独立科学任务。

每次生产模块修改后，固定执行：受影响契约测试 → 外部真实轨迹的完整生产复跑 → 少量真实模型对照 → 未用于修复的任务验证。记录哪个阶段通过、哪个阶段失败；上一轮成功不豁免新改动的集成检查。重试政策必须在实验前冻结，并同时报告第一次尝试结果和允许恢复后的最终结果。

清理代码应围绕消除重复职责展开：兼容迁移两份客户端、统一测试与生产入口、统一调用政策和结果状态。历史报告和失败轨迹是审计证据，不应作为“冗余代码”删除。没有证据支持一次性大改调度、世界模型、远跳、记忆和评价器后用一个新总分证明全部改进。
